## Context Recap (from workflows + code)

| Layer | What it does |
|---|---|
| **n8n: Stage Manager** | Runs per PO; transitions Stage1 → Stage1.5 → Stage2 → Stage2.5 → Stage3 based on date thresholds or test-mode minutes |
| **n8n: Check Email Replies** | Polls Gmail since last run; sends emails + POs to Claude for extraction |
| **n8n: Classify – Delivery Status** | Deterministic classifier: On time / Delayed / On time TBC / Delayed TBC / Shipped TBC / Unclear / No reply yet |
| **n8n: PO Followup Actions** | Sends outreach/reminders per stage based on Communication Logs state |
| **Apps Script** | Serves dashboard API. `latestClassification()` picks highest stage's classification. Buckets into `onTrack / needsAttention / awaitingReply` |
| **Dashboard** | Reads the 4 buckets. Summary panel is fully hardcoded. "What changed" is fully hardcoded. |

## 1. Making the Summary Panel Dynamic

### The Problem
The summary panel currently says things like **"4 of the 20 stalled POs are awaiting your action, not the supplier's"** — completely hardcoded strings.

### What "Summary" Should Actually Say
The summary is an **AI-generated insight sentence** — it's not a simple count. The goal is to tell the buyer: *"here's what matters right now and why."*

### Ideas

#### Option A — Compute it inside Apps Script (Simplest, no new infra)
After building `openPOs / onTrack / needsAttention / awaitingReply`, compute a structured `summary` object and return it as part of the dashboard API response.

```js
// In apps_script.js, after building the 4 buckets:
var humanReviewCount = needsAttention.filter(po =>
  normalize(comm.needs_human_review).toLowerCase() === 'yes').length;

var noResponseCount = awaitingReply.filter(po =>
  latestClassification(row) === '' || latestClassification(row) === 'No reply yet').length;

var summary = {
  headline: buildHeadline(needsAttention, awaitingReply, onTrack, openPOs),
  bullets: buildBullets(needsAttention, humanReviewCount, noResponseCount),
};
```

`buildHeadline()` picks the most urgent real signal: 
- If human review items exist → "X POs flagged for your review — supplier response was contradictory or partial"
- If delayed count > X% of open → "Y of Z open POs are delayed — action needed today"
- If all on track → "All N POs are on track, no action needed"

**Pros:** Zero new infra, real data immediately.
**Cons:** Logic-driven, not AI-generated insight. Won't say things like "3 POs are stuck because of unreleased payments."

#### Option B — Persist a daily AI summary via n8n (Better, closer to what you had)
Add a new n8n workflow step (or sub-step in existing stage-manager run) that:
1. Takes the day's aggregated PO state.
2. Calls Claude with a short prompt: *"Summarize the buyer's most urgent actions across these N POs in 2 sentences."*
3. Writes the result to a **`Dashboard Summary` sheet** (simple: date, headline, bullets JSON).
4. Apps Script reads that sheet and returns it in the dashboard API.

**Pros:** Real AI-generated prose like what's mocked today.
**Cons:** Runs on n8n schedule, not real-time. Summary may be from 2 hours ago. You'd show a "generated at X" timestamp.

#### Option C — Hybrid (Recommended)
- Apps Script computes **bullet points** deterministically (real counts, real data, instant).
- The **headline** is read from the `Dashboard Summary` sheet (AI-generated by n8n, updated on each main workflow run).
- If the sheet row is >24h old, fall back to a deterministic headline.

**Implementation for Apps Script bullet points:**
```
• X POs classified as Delayed (supplier confirmed late)
• Y POs: Delayed TBC (supplier acknowledged delay, no new date)
• Z POs flagged for human review (partial shipment / contradiction)
• N POs: no supplier response received
```
All of these can be computed from `latestClassification()` right now — no new data needed.

## 2. "What Changed Since Yesterday" — Making It Dynamic

### The Problem
Currently hardcoded strings. The concept requires knowing yesterday's state.

### Approach: Daily Snapshot in Google Sheets

Add a `PO Daily Snapshot` sheet (or a column `last_classification_date` + `last_classification_value` in Communication Logs):

| po_line_key | snapshot_date | classification |
|---|---|---|
| C1_PO001_1 | 2026-06-29 | On time |
| C1_PO001_1 | 2026-06-30 | Delayed |

**n8n writes a snapshot** once per day (beginning of day, or end of day run). Apps Script reads yesterday's snapshot, compares to today's current classification, and computes:

```js
var slippedToDelayed = 0;   // was On time/TBC, now Delayed/Delayed TBC
var recoveredToOnTrack = 0; // was Delayed, now On time
var wentSilent = 0;         // was awaiting reply, no new response in 24h
var newReplies = 0;         // supplier_reply_timestamp is from today
```

**Return from API:**
```json
"changedSinceYesterday": {
  "slippedToDelayed": 3,
  "recoveredToOnTrack": 1,
  "wentSilent": 2,
  "newReplies": 4
}
```

**Dashboard renders this dynamically** — fallback to "No changes yet today" if snapshot not available.

### Simpler version (if snapshots are too much right now)
Add 2 columns to Communication Logs: `prev_classification` and `prev_classification_date`. n8n updates `prev_classification` whenever it changes the current classification — capturing the "last known" state. Apps Script diffs `latestClassification()` vs `prev_classification`.

## 3. "Response Unclear" — Where Does It Live?

### What Happens Today
The classifier already produces `classification = 'Unclear'` when:
- Email was found (`email_found = true`)
- No dates, no confirmed on-time, no confirmed delayed
- Supplier responded but said something non-actionable

### Should It Be "Awaiting Reply" or a New Flag?

**My recommendation: Create a sub-status flag `response_unclear = true` and keep it inside "Awaiting Reply."**

Here's the reasoning:

| Scenario | What it means | Where it belongs |
|---|---|---|
| No email at all | Supplier hasn't replied | Awaiting Reply |
| Supplier replied with real info (dates, on-time confirm, delay) | Classified | On Track or Needs Attention |
| Supplier replied but didn't answer the question (vague, off-topic, partial) | **Response Unclear** | Still Awaiting Reply, but with a flag |

The buyer still needs to wait for a proper answer — so it's "awaiting" in nature. But the agent should **not** send a generic reminder** — it should send a targeted follow-up that specifically says "your last reply didn't answer our question."

### Practical Implementation

**In Communication Logs, add a column:** `stage{N}_response_unclear = TRUE/FALSE`

**In the classifier workflow** (Classify – Delivery Status), when `classification = 'Unclear'`:
```js
needs_human_review = false; // Not a human review case — it's still automatable
response_unclear = true;    // Flag for agent to handle differently
```

**In the PO Followup Actions workflow**, when checking what to do next:
- If `response_unclear = true` → send a "clarification follow-up" email instead of a standard reminder
- The clarification email references what the supplier said and asks specifically for ship date / delivery date

**In the Dashboard:**
- In the "Awaiting Reply" tab, show a sub-badge on those rows: `⚠ Unclear response`
- In the "Needs Attention" tab, do NOT include these — they're not delayed, the agent is still handling them

**Summary card could show:**
- "3 awaiting reply — including 1 with unclear response from supplier"

## 4. Human Review in the Dashboard — Workflow & Display

### What "needs_human_review = true" Means (from classifier)
Triggered when:
- Partial shipment (can't know remaining quantity without buyer judgment)
- Contradiction (supplier said "on time" but dates say "delayed" — or vice versa)
- Confidence = 'Low' from Claude

### Where Does It Live Today?
It goes into `needsAttention` (the current classifier in Apps Script catches `needs_human_review`... actually no, it only checks classification strings like "delay/risk"). **The current code does NOT handle `needs_human_review` in the dashboard API at all.**

### Proposed Workflow for Human Review

#### Step 1: n8n writes `needs_human_review = TRUE` to Communication Logs
This already happens (the classify workflow sets it). ✅

#### Step 2: The n8n PO Followup Actions workflow checks this flag
When `needs_human_review = TRUE`:
- Agent does NOT send a follow-up email to supplier
- Agent sends an **internal notification to the buyer** (email or Slack): "PO X needs your review — [reason]"
- PO stays in this state until buyer takes action

#### Step 3: Buyer acts on the dashboard
The "Needs Attention" tab should show a dedicated `Needs Review` sub-type row, clearly separate from `Delayed`. The pill should say **"Needs Review"** (already implemented in utils.js as `p-review`).

In the "Needs Attention" tab, group rows visually:
- **Delayed** rows (red pill)
- **Needs Review** rows (orange/amber pill) — the human review ones

#### Step 4: Human Review Resolution (new UI element)
On the **PO Detail page**, for human-review POs, show a visible action card:
```
⚠ This PO needs your review
Reason: Partial shipment received — quantity to be confirmed
[ Mark as reviewed — supplier info is accurate ]
[ Override classification → Delayed ]  
[ Override classification → On Track ]
```

When buyer clicks one of these, it calls the Apps Script with action=`resolveReview`:
```
?action=resolveReview&commsGroupId=XXX&resolution=delayed&sessionToken=...
```

Apps Script writes:
- `needs_human_review = FALSE`
- `human_review_resolved_by = email`
- `human_review_resolution = delayed/on_track/confirmed`
- `human_review_resolved_at = timestamp`

n8n picks this up on next run and continues the normal stage flow.

#### Summary Panel Integration
The summary card should call this out:
- "2 POs flagged for your review (partial shipment / contradiction)"

## 5. Stage Flow Clarification for On Track — Stages 1.5 and 2.5

### The Full Stage Map (from Stage Manager workflow)

```
Stage1 ──────────────────────────────────────────────────────────┐
  Actions: Send outreach email → reminders → escalation          │
  Status: Stage_Initiated → Outreach_Sent → ... → Escalation_Sent│
  When exhausted → transition to Stage1.5                        │
                                                                  │
Stage1.5 (PASSIVE LISTENING) ─────────────────────────────────── │
  No agent actions taken                                          │
  Just monitoring incoming email replies                          │
  Waiting for: date threshold (ship_by - N days) to be reached   │
  → transition to Stage2                                          │
                                                                  │
Stage2 ──────────────────────────────────────────────────────────┤
  Same as Stage1 but escalated (buyer copied, stronger tone)     │
  When exhausted → transition to Stage2.5                        │
                                                                  │
Stage2.5 (PASSIVE LISTENING) ─────────────────────────────────── │
  Same as Stage1.5                                                │
  → transition to Stage3 when next threshold reached             │
                                                                  │
Stage3 ──────────────────────────────────────────────────────────┘
  Final escalation stage
```

### How This Maps to Dashboard Classification

| Stage | follow_up_status | What it means for classification |
|---|---|---|
| Stage1 | Stage_Initiated | No outreach sent yet — Awaiting Reply |
| Stage1 | Outreach_Sent, Reminder1_Sent... | Agent is actively chasing — Awaiting Reply |
| Stage1 | Escalation_Sent | Final action sent in Stage1 — Awaiting Reply |
| **Stage1.5** | **Monitoring_Reply** | **Agent waiting silently — Awaiting Reply** |
| Stage2 | Stage_Initiated | Threshold triggered, new stage starts — Awaiting Reply |
| **Stage2.5** | **Monitoring_Reply** | **Silent wait again — Awaiting Reply** |
| Stage3 | Stage_Initiated+ | Last escalation — Needs Attention (no response) |

So Stages 1.5 and 2.5 should always be in **"Awaiting Reply"** on the dashboard. The classification pill should reflect the *delivery classification*, not the stage — but the "what's happening" column and the detail page should clearly say "Monitoring — waiting for supplier reply."

### Proposed Dashboard Changes for Stage Display

**In the "Awaiting Reply" table**, add a "Stage" column (or include it in the "Last update" column):

```
Monitoring reply (Stage 1 escalated, listening for response)
```

**In utils.js `nextTouchPoint()`**, enhance it:
```js
export function nextTouchPoint(po) {
  if (po.next_touch_point) return po.next_touch_point;
  const stage = po.follow_up_stage || '';
  const status = po.follow_up_status || '';
  if (stage === 'Stage1.5' || stage === 'Stage2.5') {
    return 'Monitoring inbox — no action pending';
  }
  if (status === 'Stage_Initiated') return 'Outreach pending';
  return 'Monitoring';
}
```

**For On Track classification during 1.5/2.5:**
A PO can be in Stage1.5 but have `classification = 'On time'` because the supplier already replied! In that case:
- Dashboard tab: **On Track** ✅
- The stage (1.5/2.5) is irrelevant to the buyer — the delivery is confirmed on time.

This means the classification takes priority over the stage for bucketing. The stage only matters for "what the agent is doing next," which only shows in the detail view and in "Awaiting Reply" rows.

## 6. Series of Emails — Capturing Multi-Email Threads

### The Problem
A supplier might reply to a follow-up email in 3 emails:
1. "We'll check and revert" (vague)
2. "The production is done" (still no date)
3. "Shipment will go out 10 July" (actual date — this is the answer)

The current system checks since the `last_run_timestamp`. If all 3 arrive between runs, Claude sees all 3. But how do we know email 3 is the "final" answer and email 1 wasn't?

### Current Behavior
The n8n `Check Email Replies - Each Supplier v6` workflow:
- Fetches **all emails since last run** in one batch
- Passes **all of them as formatted context** to Claude
- Claude extracts per PO, referencing the most relevant email

So Claude is already seeing the full thread context. If email 3 has a date, Claude will pick it up.

**The real problem** is: what's stored in Communication Logs? Currently it stores the **final classification result** from one Claude run. There's no concept of "partial answer in progress."

### Proposed Solution: Thread State Tracking

#### Option A — Intermediate `thread_in_progress` state
Add to Communication Logs:
```
stage1_thread_started = TRUE
stage1_thread_start_email_message_id = <id>
stage1_thread_start_timestamp = 2026-06-30T10:00:00
stage1_last_email_timestamp = 2026-06-30T11:30:00
stage1_thread_resolved = FALSE
```

When the supplier replies but doesn't provide complete info (`classification = 'Unclear'` or `response_unclear = true`):
- Set `thread_in_progress = TRUE`
- Keep the classification as `response_unclear`
- Agent sends a clarification follow-up specifically referencing their last message

When the supplier provides a complete answer:
- Set `thread_in_progress = FALSE`, `thread_resolved = TRUE`
- Update the classification normally

**Dashboard shows during thread_in_progress:**
- Bucket: **Awaiting Reply**
- Sub-badge: `  Replied — clarifying`
- "What's happening": "Supplier partially responded — awaiting complete info"

#### Option B — Rely on Claude's multi-email analysis (Simpler)
Since Claude already sees ALL emails since last run, trust it to correctly assess the most recent and complete response. Add to the Claude prompt:

> "If there are multiple emails from the supplier in a thread, treat the sequence as a conversation. If the latest email in the thread provides a complete answer, use it. If the conversation is ongoing and incomplete, classify as 'Unclear' and set `thread_ongoing = true`."

Claude returns `thread_ongoing: true` as part of its JSON. n8n writes this to Communication Logs. The dashboard uses it to show the sub-badge.

This is simpler and leverages Claude's existing context window. **Recommended first approach.**
