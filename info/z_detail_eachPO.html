PO line item detail panel — build spec

Self-contained build kit. Pair with the three reference mocks: detail_delayed, detail_ontrack, detail_awaiting. Open those alongside this doc — they are the visual source of truth; this doc is the data and logic source of truth.

0. How to use this document

  • The mocks show what it looks like. This doc says what data drives it and how the conditional cases behave. Build the static look from the mocks, wire the data and logic from here.
  • Where you see a CAT 4 or a “Prabhas” flag, that part genuinely isn’t defined yet. Build everything around it; don’t guess the missing logic.
  • Where the doc says “use judgment,” it reflects how Prabhas has been doing it by hand. Follow that as the default. If a real case doesn’t fit, make a reasonable call and note it — don’t stall.
  • When you are genuinely unsure and it’s not covered here, ask Prabhas. A 30-second question beats a wrong build. But try the doc and the mocks first.
  • You may upload this doc + the three mocks to a GenAI assistant to scaffold the build. It will get you most of the way on the UI and display logic. The data pipeline (sheet joins, the n8n wiring, the four CAT-4/Prabhas items) still needs your own work.

1. Two separate jobs — don’t conflate them

There are two workstreams. This spec is only the second one.

  • Job A — data layer (mostly separate work). Prepares and maps clean rows into the sheets: the classification logic, the transit-time lookup table, ship-by computation, the three-sheet joins, the timezone source per client. By the time the panel reads a row, these are already done and sitting in the sheet as plain values.
  • Job B — this panel (your build). Reads the prepared rows and renders them. The panel does almost no computation. The only true panel-side transforms are timezone display formatting and quantity + unit concatenation. Everything else is bind-as-is or a conditional render rule.
Assume the data layer hands you clean, pre-computed rows. If a value you need isn’t in the sheet yet (e.g. tracking, classification), that’s a Job A gap — flag it, don’t try to compute it inside the panel.

7. The trail render loop (follow these steps in order)

  1. Read the row for this po_line_key (joined across the three sheets).
  2. Place PO issued at the top (issue_date).
  3. For each stage in order 1, 2, 3: if any milestone in that stage fired, draw the stage header (PO confirmation / Order progress / Dispatch). If the stage never started, skip it entirely.
  4. Within a stage, gather every fired email send, every fired call, and every reply (including the stage’s _5_ window reply). Sort by timestamp.
  5. Render each milestone: email send (with “No reply received” if none), or call (reply nested inside if answered), or a standalone “Supplier reply received” for an unprompted _5_ window reply.
  6. After any reply, check its classification: if Delayed / At risk / Needs review, append a Flagged for buyer review milestone. If On time / On time-TBC, don’t.
  7. After the last stage: if the line is terminal (escalated with no next step, dispatched, or PO closed) render no next touch point. Otherwise render the Next touch point (grey dot).

ConditionRender rule
Reply by emailSeparate milestone from the prompting email. Show send, then “Supplier replied · [time]”, then reply box
Reply by callNested inside the call milestone. “...call placed” + “Supplier responded on the call” + reply box
Unprompted reply (1.5 / 2.5 window)Standalone “Supplier reply received” milestone, under the header of the stage it followed (1.5→PO confirmation, 2.5→Order progress). Window number never shown
Two replies in one stageBoth render as separate milestones in time order. Keep both. Differing tags show the trajectory
Every reply, regardless of channelShows the same three things: classification tag, short status, long response

14. Global display conventions

  • Empty = dash (–), same color as filled values. Never “not recorded”/blank. Exception: timeline never renders not-fired events.
  • Partial value (e.g. one tracking field): show what’s present, dash the missing. Don’t hide the whole element.
  • Customer-facing labels only. Variable names never appear in the UI.
  • Dots green for events that happened; Next touch point dot grey. Channel shown by badge, not dot color.
  • Status color (red/gold/green/purple) only in pills and reply tags, never as a box background.
  • Font hierarchy: milestone titles largest in the trail; dates/secondary clearly smaller.

16. Blocked on Prabhas (the only real unknowns)

Everything else is fully specified. Build it all; get these four from Prabhas before wiring the logic they govern.
  1. Classification logic (CAT 4) — turns a reply into one of six values. Biggest dependency: pills, tags, routing, escalation all key off it.
  2. Next-touch-point algorithm (CAT 4, Job A) — compute next action + date from stage + status + bands.
  3. Timezone per client — UTC stored; display target set at onboarding. Biotique IST; EST for US demo.
  4. Tracking node (CAT 3) — which n8n node parses carrier + number, so Job A can persist them.
Judgment, not a blocker: where the doc says “use judgment” (e.g. an unusual reply that doesn’t fit a stage, a missing contact name), follow how the mocks and Prabhas’s pattern handle it, make a reasonable call, note it, and move on. Ask Prabhas only when genuinely stuck.
