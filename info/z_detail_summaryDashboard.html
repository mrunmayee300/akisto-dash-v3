Dashboard (four-view page) — build spec

Self-contained build kit for the main dashboard. Pair with the reference mock dashboard_v3 (the four-tab page with summary banners + count tiles). The mock is the visual source of truth; this doc is the data and logic source of truth. Companion to the detail-panel spec; clicking a row opens that panel.

0. How to use this document

  • The mock shows what it looks like. This doc says what data drives it and how the conditional cases behave. Build the look from the mock, wire data and logic from here.
  • CAT 4 / “Prabhas” flags mark logic that isn’t defined yet. Build around them; don’t guess.
  • “Use judgment” means follow the mock and Prabhas’s established pattern; make a reasonable call and note it rather than stalling.
  • Ask Prabhas only when genuinely stuck after trying the doc and mock.
  • Uploadable to a GenAI assistant with the mock to scaffold the UI. The categorization logic and the data pipeline remain your own work.

1. Two separate jobs — don’t conflate them

  • Job A — data layer (separate work). Produces, per PO line: the classification (which decides the view), the delivery-status sentence, and the aggregate numbers (tile counts and the “since yesterday” deltas). The dashboard receives these as ready values.
  • Job B — this dashboard (your build). Reads the prepared rows + aggregates and renders the four views, banners, and tiles. It filters and displays; it does not classify or compute aggregates itself.
The categorization that sorts a line into On track / Needs attention / Awaiting reply is the same classification logic that drives the detail-panel pills. It is one shared dependency, not a new one. (Prabhas to define; may be Sheet formulas or a function.)

3. Page structure

  • Header: brand + the active view label + buyer name/date (top-right).
  • Summary banners (two, side by side): “Summary” (the action-needed call-out) and “What changed since yesterday”. Persistent across all four tabs (rendered once, above the tabs).
  • Count tiles (four): Open POs, On track, Awaiting reply, Need attention. Also persistent above the tabs.
  • Tabs (four): Open POs (default), Needs attention, On track, Awaiting reply. Each shows a table.
  • Left spine is identical across all four tables (PO, Supplier, Material code, Material description, Quantity, then status) so switching tabs doesn’t visually jump. Each view extends right with its own columns.

The “since yesterday” deltas need a stored snapshot. To compute “3 POs slipped to delayed” the system must compare today’s state to yesterday’s. That snapshot mechanism doesn’t exist yet. Job A / Prabhas. If not available at build time, the dashboard can hide this banner or show a placeholder.

8. Row-click behaviour

Clicking any PO line row opens that line’s detail page (the PO line item detail panel, specified in its own doc). Pass the row’s po_line_key. Nothing else about the detail view needs documenting here.

9. CONDITIONAL: row and view rules

ConditionRender rule
Line is openAppears in Open POs, and in whichever of the three filtered views its classification maps to
Line is closed (po_status = Closed)Out of scope for these open-order views. (Past/closed orders are a separate, not-yet-built surface — see blocked items.)
A view has many near-identical rows (e.g. lots of “dispatch pending”)Still list each line; this is expected. Don’t dedupe. (Earlier design note: “dispatch pending within ship-by” classifies as Awaiting reply, not Needs attention, so it doesn’t flood the attention view.)
unit_of_measure blankQuantity shows the number only
A view is empty (no lines in that state)Show an empty-state line (e.g. “Nothing needs attention right now”). Use judgment on wording per view
“Showing N of M” footerReflect the count for that view; “view all” expands

10. Global display conventions

  • Shared left spine (PO → status) identical in order and width across all four views, so tab-switching doesn’t jump.
  • Pill colors: red Delayed, gold At risk, purple Needs review, green On time, grey On time-TBC, blue Awaiting reply. Same set as the detail panel.
  • Empty value = dash (–), same color as filled values.
  • Customer-facing labels only. No variable names, no comms_group_id (internal, never shown).
  • Banners + tiles persist across all four tabs (rendered once, above the tabs).
  • US spelling, no em dashes in any displayed copy.

11. Worked example (a few real lines → views)

INPUT: three open lines
L1 300656/1, Personal Brushes (S16), FCONS01106 Brush..., qty 1,186,711, deliver-by 6/20, classification Delayed, text “Order on hold pending advance payment...”
L2 300655/6, Green Elements (S20), FCONS01103 Toothbrush, qty 10,000, ship-by 6/14, classification On time, text “Shipped 14 Jun, on/before ship-by”
L3 300661/3, Mahima Biotech (S17), FRM00461 SLES, qty 30,000, deliver-by 6/20, classification Awaiting reply, last reply none since 12 Jun.
OUTPUT: where each appears
Open POs tab: all three rows, each with its pill, no trailing column.
Needs attention tab: L1 only, with “What’s happening” = its delivery_status_text and a Delayed pill.
On track tab: L2 only, with “Delivery status” sentence and On time pill, using ship-by date.
Awaiting reply tab: L3 only, “Last update” = “No reply since 12 Jun”, “Next touch point” from Job A, Awaiting reply pill.
Tiles: Open 3, On track 1, Awaiting 1, Need attention 1 (all Job A aggregates).
Row click: clicking L1 opens the detail panel for po_line_key C1_300656_1.

12. Blocked on Prabhas (the only real unknowns)

Build everything else. Get these from Prabhas before wiring the logic they govern.
  1. Classification logic (CAT 4) — the same shared dependency as the detail panel. Decides view routing, pills, and tile counts. Sheet formula or function, Prabhas to decide.
  2. Tile counts & summary aggregates (CAT 4, Job A) — computed upstream from the classified dataset.
  3. “Since yesterday” deltas (CAT 4, Job A) — need a stored daily snapshot to diff. Mechanism not built. If unavailable, hide the banner.
  4. Next touch point (CAT 4, Job A) — same computation as the detail panel.
  5. Past / closed orders — these views are open-orders only. Where closed orders live is a separate, not-yet-designed surface.
Judgment, not a blocker: empty-state wording per view, footer counts, and how long a row may wrap — follow the mock and make a reasonable call. Ask Prabhas only when genuinely stuck.
